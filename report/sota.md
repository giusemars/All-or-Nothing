# Syscall Restriction and Atomic Code Execution: Literature Overview

Nov 3, 2026 · @Giuseppe

There is a lot of work on both questions. Restricting a process to its "intended" syscalls is a well-studied area. Kernel-enforced start-to-finish execution of user code has fewer direct results, and the closest come from trusted execution, embedded attestation and in-process isolation.

This list was compiled from memory, without looking anything up. Check titles, authors and venues before citing.

## 1. Restricting a process to its intended system calls

The closest match is BASTION. It checks three things: the syscall type, the control-flow path to it, and its arguments.

### Paper summaries

**A Sense of Self for Unix Processes (Forrest et al., 1996).** The idea comes from the immune system, which learns to tell "self" from "non-self." The authors run a privileged program (like sendmail or lpr) normally and record every system call it makes. They slide a small window (e.g., 6 calls long) over this trace and store every short sequence they see in a database: this is the program's "normal behavior." Later, while the program runs for real, each new window is checked against the database. A sequence never seen before is a mismatch, and many mismatches in a short time suggest the program has been taken over. The key finding is that these short sequences are a surprisingly stable fingerprint of a program. The limits: the model is learned from examples, so rare but legitimate behavior causes false alarms, and an attacker who knows the model can craft an attack that only uses "normal-looking" sequences (a mimicry attack).

**Intrusion Detection via Static Analysis (Wagner & Dean, 2001).** Instead of learning what a program normally does, this paper reads the program's source code and works out which sequences of system calls are even possible. It turns the code into an automaton, a state machine that accepts only the legal syscall orders. A monitor then follows the running program and raises an alarm if a syscall arrives that the automaton does not allow at that point. The paper offers several models: a simple one built from the call graph (which function can call which), a more precise one that also tracks function calls and returns like a stack (a pushdown automaton), and a cheap one that only checks pairs of consecutive calls. Because the model comes straight from the code, legitimate behavior never triggers an alarm. The trade-off is precision versus speed: the most precise model can be very slow to check. This "derive the allowed syscalls from the code" framing underlies most later work on intended syscalls.

**Systrace: Improving Host Security with System Call Policies (Provos, 2003).** Systrace places itself between a program and the kernel (this is called syscall interposition): every system call the program makes is checked against a policy before the kernel runs it. A policy is a list of rules such as "this program may open files only under /var/www." Writing policies by hand is tedious, so Systrace can generate one by watching a normal run, and then asks the user about anything new. It also supports privilege elevation: instead of making a whole program run as root (setuid), you can grant root rights for just one specific call. The paper also covers a classic pitfall of interposition: the program could change a syscall's arguments in memory after the check but before the kernel uses them (a race condition), and Systrace copies the arguments to avoid this. Janus and Ostia are earlier and later designs of the same family.

**Authenticated System Calls (Rajagopalan et al., 2005).** Before a program is installed, a trusted tool analyzes it and finds every place where it makes a system call. For each place, it writes down a small policy: which syscall is made there, from which address, and what the arguments can be. The tool then rewrites the call so it carries this policy together with a MAC, a cryptographic "signature" computed with a secret key that only the kernel knows. When the program runs, the kernel recomputes the MAC on every syscall and refuses the call if it doesn't match or if the real call breaks the policy. An attacker who injects code, or who reuses existing code in an unexpected way, can't produce a valid MAC because they don't know the key. The result is that a program can only make the syscalls that appear in its code, from the right places and with allowed arguments, without a separate monitoring process.

**sysfilter (DeMarinis et al., 2020).** Most programs only need a small part of the roughly 350 Linux system calls, but by default they can use all of them, which gives an attacker plenty of tools after a takeover. sysfilter automatically works out which syscalls a program really needs, using only the compiled binary (no source code). It builds a function-call graph across the program and all the shared libraries it loads (like libc), and collects the syscalls reachable from the program's entry point. The analysis errs on the safe side: it may allow a few unneeded calls, but it should never block a needed one. The resulting allowlist is enforced with seccomp-BPF, the Linux feature that lets a process install a small filter program that the kernel runs on every syscall to allow or deny it. Tested on thousands of Debian programs, it removes a large share of the reachable syscalls without breaking them.

**Confine (Ghavamnia et al., 2020).** Containers such as Docker already filter syscalls with seccomp, but the default profile is generic: it has to work for every container, so it allows around 300 syscalls. Confine builds a profile tailored to each container image. It first runs the container to see which programs actually execute inside it. It then analyzes those programs and the libraries they use (including the various libc versions found in images) to find every syscall they can reach. The union of these becomes the container's seccomp profile, typically far smaller than the default. The authors also check known Linux kernel vulnerabilities and show that many of them can no longer be triggered from inside a container that uses its Confine profile.

**Temporal System Call Specialization (Ghavamnia et al., 2020).** A server program lives in two phases. During startup it reads its configuration, opens files, binds network sockets and maybe starts helper processes. After that it enters a long serving phase where it just handles requests in a loop. Many dangerous syscalls (such as execve, which starts a new program) are needed only during startup. This paper finds the point in the code where startup ends, computes which syscalls are reachable from there onwards, and installs a second, stricter seccomp filter at that moment. Since attacks usually arrive through requests, i.e., during the serving phase, the attacker faces the smaller list. For many popular servers this removes execve and similar calls completely, which a single filter covering the whole lifetime can't do.

**C2C: Fine-grained Configuration-driven System Call Filtering (Ghavamnia et al., 2022).** Programs like Nginx or Redis contain code for many optional features (e.g., TLS, compression, logging to a file), and each deployment turns on only some of them through its configuration file. A filter built from the whole program must allow syscalls for every feature, even unused ones. C2C links each configuration option to the code it enables and then to the syscalls that code can reach. Given a real configuration file, it computes a filter that allows only syscalls for the features that are switched on. Combined with the startup/serving split from the temporal specialization work, this gives noticeably tighter filters than analyzing the program as a whole.

**Chestnut: Automating Seccomp Filter Generation for Linux Applications (Canella et al., 2021).** Chestnut's goal is to make seccomp filters something developers get almost for free. It works in two ways. If source code is available, a compiler plugin (an LLVM pass) records which syscalls the program and its libraries can make while the program is being built. If only the binary is available, a binary analysis finds syscall instructions and the syscall numbers they use. An optional third step runs the program under tracing to see which syscalls are really used, and can tighten the filter further. The paper discusses the basic trade-off: static analysis over-approximates (allows a bit too much, but never breaks the program), while dynamic tracing under-approximates (tight, but may miss a rarely used path and crash the program later).

**SysXCHG: Refining Privilege with Adaptive System Call Filters (Gaidis et al., 2023).** On Linux, once a process installs a seccomp filter it can only add more filters, never remove one, and the filters stay in place even when the process calls execve to become a different program. So when a shell or a server launches helper programs, the filter must allow everything that every one of those programs might need. SysXCHG fixes this by giving each program file its own filter and letting the kernel exchange the active filter at execve time, so each program runs with exactly its own list. This is done safely, so a process can't use the mechanism to escape a filter it already has. The authors implement it in the Linux kernel, show it works on real exec chains, and measure low overhead.

**Nibbler (Agadakos et al., 2019).** Shared libraries like libc contain thousands of functions, but a given program uses only a fraction of them. The unused code still sits in memory, and attackers can use it: in code-reuse attacks (such as return-oriented programming, ROP), the attacker chains together small snippets of existing code, called gadgets, instead of injecting new code. Nibbler analyzes the program and its libraries at the binary level, builds a call graph, and finds library functions that the program can never reach. It then overwrites those functions so they can't run. This shrinks the pool of gadgets and also reduces the set of syscalls the process can reach, which makes a later syscall filter tighter. The authors show that a large share of library code can be removed without breaking the programs.

**Shredder and Saffire (Mishra & Polychronakis, 2018 / 2020).** Both papers go beyond "which functions may be called" to "with which arguments." Shredder targets Windows programs: many attacks end by calling a powerful system API (for example, one that makes memory executable or starts a process). Shredder uses static analysis to find which argument values the program itself passes to these APIs, and blocks calls with other values at runtime. Saffire applies the idea more generally with function specialization: for each place in the code that calls a sensitive function, it creates a private copy of that function that only accepts the argument values used at that place. An attacker who jumps into or reuses the function with their own arguments then gets rejected, because the hard-coded expectations don't match.

**BASTION: Practical Defense against Control-Flow Hijacking via System Call Context (Jelesnianski et al.).** In a control-flow hijacking attack, the attacker redirects a program's execution, usually to reach a powerful syscall like execve (start a program) or mprotect (make memory executable). BASTION protects these sensitive syscalls by checking three kinds of context every time one is made. Call-type context: the syscall must be reached the way the program normally reaches it, for example through a direct call and not through a function pointer if the program never does that. Control-flow context: the chain of function calls that led to the syscall (the call stack) must be a path that really exists in the program. Argument integrity context: the arguments must hold values the program legitimately set, not values an attacker overwrote. A compiler pass gathers the needed information at build time and a runtime monitor enforces it, with low reported overhead. Check the venue before citing.

**Draco (Skarlatos et al., 2020).** seccomp filters are small BPF programs that the kernel runs on every syscall, and with the long filters used for containers this adds noticeable cost to syscall-heavy workloads. Draco's insight is that programs tend to repeat themselves: the same syscall is made again and again with the same arguments. So once a syscall and its arguments have been checked and allowed, the result can be cached, and later identical calls skip the full filter. The paper presents two versions. A software version adds this cache to the Linux kernel. A hardware version adds a small dedicated cache to the CPU and performs the checks in parallel with normal execution. The hardware version brings checking cost close to zero.

**Jenny (Schrammel et al., 2022).** Intel MPK (Memory Protection Keys, also called PKU) lets a program tag pages of its memory with one of 16 keys and switch, very quickly and without the kernel, which keys the current thread can access. This allows isolated compartments (sandboxes) inside a single process. The problem is that syscalls bypass this protection: the kernel ignores protection keys when it accesses memory, so a sandboxed component could, for example, ask the kernel to read or remap memory belonging to another compartment. Jenny closes this gap by intercepting syscalls made from each compartment and filtering them with a per-compartment policy. It compares several interception methods (ptrace, seccomp, and Linux syscall user dispatch) for speed, and handles tricky cases like signals, memory mapping and shared file descriptors. Its main point is that in-process isolation is only sound if syscalls are filtered too.

OpenBSD's `msyscall`/`pinsyscalls` and `pledge` are the deployed version of "syscalls only from approved call sites."

### Paper summaries

**Flicker (McCune et al., 2008).** Flicker lets you run a small, security-critical piece of code (called a PAL, Piece of Application Logic) in total isolation, even if the operating system is compromised. It relies on a CPU feature called late launch, or dynamic root of trust (AMD SKINIT, Intel TXT). This instruction pauses everything, resets the CPU into a clean state, and starts a chosen block of code from its first instruction. The CPU also records a hash of that code in the TPM, a small security chip on the motherboard. The PAL runs with interrupts off and nothing else executing, then hands control back to the OS. Later, the TPM can prove to a remote party exactly which code ran (remote attestation). The trusted code base is tiny, but each Flicker session is slow (milliseconds or more), so it suits rare, high-value operations.

**TrustVisor (McCune et al., 2010).** TrustVisor keeps Flicker's goal, isolated execution of small code modules, but makes it fast. Instead of a late launch for every call, it starts once a very small hypervisor, a thin layer running beneath the OS with more privilege. The hypervisor uses nested page tables, a hardware feature that lets it control which physical memory the OS can see, to hide each registered PAL's code and data from the OS. A PAL can only be entered at its registered entry points. TrustVisor also gives each PAL a software "micro-TPM" for attestation and for sealing data (encrypting it so only that PAL can decrypt it). Entering a PAL becomes much cheaper than in Flicker, while the hypervisor stays small enough to trust.

**Fides (Strackx & Piessens, 2012).** Fides is a hypervisor that protects selected parts (modules) of an application, both from a compromised kernel and from the rest of the same process. Its rules are simple. A module's data can only be read or written while the module's own code is running. The module's code can only be entered through entry points the module declares; a jump to any other address inside it is blocked. This is the program-counter-based access control model, where what memory is allowed depends on where the instruction pointer currently is. Modules can also check each other's identity and communicate securely. The paper is one of the clearest descriptions of the "protected module with controlled entry" model, which later shaped hardware designs.

**Sancus (Noorman et al., 2013).** Sancus brings the protected-module idea into hardware for tiny, cheap devices (sensor nodes, IoT), by extending an open-source MSP430 microcontroller. The CPU itself checks every memory access against the current program counter: a module's data is accessible only while the module's code runs, and its code can only be entered at a single designated entry point. The hardware also derives a secret key for each module from its code, so a module can prove to a remote party that it is genuine (remote attestation) and communicate securely. None of this depends on trusting the OS or other software on the device. A later version, Sancus 2.0, extends the design and its evaluation.

**Intel SGX (Intel).** SGX (Software Guard Extensions) lets a normal user-space program create an enclave, a region of memory that the CPU encrypts and protects, so even the OS and hypervisor can't read or change it. The relevant property for your question is controlled entry. Code outside can enter an enclave only with the special EENTER instruction, and EENTER always jumps to the entry address defined in a Thread Control Structure (TCS) set up when the enclave was created. Jumping into the middle of enclave code is impossible. If an interrupt arrives while the enclave runs, the CPU performs an Asynchronous Enclave Exit, which saves and hides the enclave's registers, and execution later continues with ERESUME. SGX is a reference design for controlled entry, but many side-channel attacks have been published against it, and Intel has dropped it from consumer CPUs (it remains on servers).

**SMART (Eldefrawy et al., 2012).** SMART adds remote attestation to very cheap microcontrollers with only small hardware changes. Remote attestation means a remote verifier can check that a device's memory hasn't been tampered with: the device computes a cryptographic checksum of its memory with a secret key. SMART puts the attestation code in read-only memory and makes the secret key readable only while the program counter is inside that code. Crucially, the hardware enforces that the code can be entered only at its first instruction and left only from its last, with interrupts disabled throughout. So the code runs atomically: an attacker can't jump into the middle to skip checks and grab the key. This is one of the earliest designs that enforces exactly the property in your second question for a specific block of code.

**TrustLite (Koeberl et al., 2014).** TrustLite generalizes SMART into a flexible security architecture for embedded devices. Its core is an Execution-Aware Memory Protection Unit (EA-MPU). A normal MPU sets access rights for memory regions; an execution-aware one makes those rights depend on which code is currently running. This allows several isolated software modules, called trustlets, to share one small device, each with private memory. A trustlet can only be entered through its defined entry points. Unlike SMART, TrustLite allows interrupts: when one arrives, the trustlet's state is securely saved and its registers cleared so no secrets leak, and the trustlet resumes safely later. This shows how to get controlled entry and isolation without the strict "no interrupts" rule.

**VRASED (De Oliveira Nunes et al., 2019).** VRASED is a remote attestation design for small microcontrollers in which both the hardware and the software are formally verified, i.e., mathematically proven to satisfy their security properties. A small hardware monitor watches the program counter and memory accesses. One of the proven properties is atomicity: the attestation code can be entered only at its first instruction, can be left only from its last, and can't be interrupted. If any of these rules is broken, for example by a jump into the middle of the code, the hardware immediately resets the device and wipes sensitive state. A half-executed attestation therefore never produces a valid result. The design runs on an MSP430-based core and adds very little hardware.

**APEX: Proofs of Execution (De Oliveira Nunes et al., 2020).** Attestation proves what code is in memory, but not that it actually ran. APEX extends VRASED to prove that a specific block of code was executed, and that a given output really came from it. A small hardware module watches the program counter. It sets a flag, called EXEC, only if the block starts at its first instruction, runs to its last instruction without jumping out, without interrupts, and without anything else modifying the block's code or output memory. Any violation clears the flag. The flag is included in the attestation, so a remote verifier receives a cryptographic proof that the code ran from start to finish. This is very close to your second question, though it targets embedded hardware rather than a general-purpose OS kernel.

**ERIM (Vahldiek-Oberwagner et al., 2019).** ERIM isolates a trusted component (for example, the part of a web server that holds TLS keys) inside the same process as untrusted code, using Intel MPK. With MPK, memory pages are tagged with keys, and a CPU register called PKRU says which keys the current thread may access. PKRU is changed by a user-space instruction, WRPKRU, which makes switching between components very fast (tens of cycles) but creates a danger: an attacker who hijacks control flow could jump straight to a WRPKRU instruction and unlock the trusted memory without going through the proper entry. ERIM solves this in two steps. It scans the program's binary, and rewrites it where needed, so that WRPKRU appears only inside designated call gates. Each gate places a check right after WRPKRU that verifies the new PKRU value is the expected one, and aborts otherwise. Jumping into the middle of a gate therefore achieves nothing. This is a direct, practical answer to the "no jumping into the middle" problem.

**Hodor (Hedayati et al., 2019).** Hodor introduces protected libraries: shared libraries (such as a database's storage engine) whose memory is isolated from the application that uses them, yet which can be called almost as cheaply as normal functions. Calls go through small trampolines that switch on the library's access rights on the way in and switch them off on the way out. Hodor offers two switching mechanisms: Intel MPK (the WRPKRU instruction) or Intel VT-x's VMFUNC, which lets code switch between page tables prepared by a hypervisor. Like ERIM, it must stop an attacker from running these switch instructions outside the trampolines. Hodor scans code pages when they become executable, and if it finds a stray switch instruction it can't remove, it sets a hardware watchpoint (a debug register that traps when a given address is executed) on it. Evaluations on systems like Redis show low overhead.

**Light-weight Contexts (Litton et al., 2016).** An lwC (light-weight context) is a new OS abstraction: a single process can hold several lwCs, each with its own view of memory, its own open file descriptors and its own permissions. Unlike threads, lwCs are isolated from each other; unlike separate processes, switching between them is cheap. Switching is done through the kernel, and an lwC always resumes exactly where it last switched away, so other code can't enter it at an arbitrary point. The authors show several uses: snapshotting a server process and quickly restoring a clean copy for each user session (so one session can't affect another), isolating sensitive data such as keys inside one lwC, and building reference monitors. Switching costs are much lower than switching between processes.

**kBouncer (Pappas et al., 2013).** kBouncer defends against return-oriented programming (ROP). In ROP, the attacker chains many small existing code snippets (gadgets), each ending in a return instruction, to build a malicious program out of the victim's own code. kBouncer uses the Last Branch Record (LBR), a set of CPU registers that always holds the last 16 or so branches the program took (source and destination addresses). When the program calls a sensitive Windows API (e.g., to create a process or change memory protection), kBouncer reads the LBR and looks for ROP signs: returns that jump to an address not right after a call instruction (normal returns always do), and long sequences of very short code fragments. Because it checks only at those API calls and the hardware records branches for free, overhead is tiny. Later research showed attackers can design gadget chains that fit the heuristics and evade it.

**ROPecker (Cheng et al., 2014).** ROPecker also uses the LBR to spot ROP attacks, but checks much more often than kBouncer, not just at sensitive API calls. It keeps only a small "window" of code pages executable at any time, the pages the program is currently using. When execution moves outside the window, the CPU traps to ROPecker. At each trap it inspects the recent branch history in the LBR and also looks ahead, simulating the likely upcoming code path, to detect chains of gadgets. This lets it catch ROP attacks that never pass through a protected API. Like kBouncer, it relies on heuristics (e.g., gadget length and chain length), so carefully crafted attacks have been shown to evade it.

**Griffin (Ge et al., 2017).** Griffin enforces control-flow integrity (CFI) from the kernel, on programs that are not recompiled. CFI means checking that every jump, call and return goes only to a target the program's code allows. Griffin uses Intel Processor Trace (PT), a CPU feature that records the program's complete control flow (every taken branch) into a memory buffer in a compressed form, with low overhead. The kernel decodes this trace and checks it against a CFI policy. It supports policies of different strength, from coarse (any valid function start) to fine-grained, plus a shadow stack check that every return goes back to its real caller. Checks happen when the program does something security-sensitive, such as a syscall, so an attacker is caught before they can do real damage. The paper studies how stricter policies cost more trace-decoding time.

**FlowGuard (Liu et al., 2017).** FlowGuard also uses Intel PT to enforce CFI on unmodified binaries, and focuses on making it fast. Fully decoding PT traces is expensive, so FlowGuard prepares ahead of time. It builds a control-flow graph of the program offline, then runs the program through fuzzing (automated testing with many random inputs) to mark which paths are actually taken in normal use. At runtime, when a security-sensitive syscall happens, a fast check compares the compressed trace directly against these known-good paths without fully decoding it. Only paths not seen before go through a slow, precise check. The result is low overhead with security close to fine-grained CFI.

**Fast Mutual Exclusion for Uniprocessors (Bershad et al., 1992).** On a single-processor machine, the only way an operation like "read a counter, add one, write it back" can be broken is if the thread is preempted (paused by the scheduler) in the middle and another thread runs. The usual fix is hardware atomic instructions or locks, which were expensive or missing on some CPUs. This paper introduces restartable atomic sequences: short code sequences that the kernel knows about. If the kernel preempts a thread while it is inside one, it moves the thread's instruction pointer back to the start of the sequence before resuming it. The sequence either runs to the end without interruption or starts over, never continuing from the middle. This gives atomicity cheaply in software, and is an early example of the kernel guaranteeing that a block of user code is never resumed partway through.

**Linux rseq (Desnoyers, Turner).** Restartable sequences (rseq) bring the 1992 idea to modern multi-core Linux. They let a thread update per-CPU data (for example, a per-CPU memory allocator cache) without atomic instructions or locks. A thread registers a small shared structure with the kernel. Before entering a critical section, it describes that section with three addresses: start, end, and an abort handler. If the thread is preempted, moved to another CPU, or interrupted by a signal while its instruction pointer is between start and end, the kernel redirects it to the abort handler instead of letting it resume mid-section. The handler can then simply retry. So the section either completes uninterrupted on one CPU or is restarted from scratch. glibc registers rseq by default, and it is used in allocators such as tcmalloc. Note that rseq guarantees atomicity against preemption; it is not a security mechanism against malicious jumps.

Intel CET IBT and ARM BTI give coarse hardware support. Indirect branches can only land on marked instructions, which stops arbitrary mid-block jumps but not jumps to another valid landing pad.
